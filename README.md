# LOGIN : 人

용인종합사회복지관 북한이탈주민 지원사업 웹사이트. 개발 인계서(2026-10-07)를 기능 기준으로, 디자인 시안 v1.3을 시각 기준으로 구현했다.
**Cloudflare Pages + Pages Functions + D1**에서 실행된다.

## 구조

```
public/                  Pages 정적 출력 디렉터리 (build output directory)
  static/styles.css      스타일
  _routes.json           /static/* 은 정적 파일, 나머지는 Functions
functions/
  [[path]].js            Pages Functions 진입점(모든 경로) → src/app.js
migrations/              D1 스키마(0001~0010), 0011 = 간소화 신청·승인 10명 제한·이용 중지·재설정 코드·게시판·신청서/동의서 양식·최신(2차 수정본) 프로그램
.github/workflows/ci.yml  PR·main 테스트
src/
  app.js                 요청 처리(라우팅·세션·CSRF·보안 헤더)
  config.js, site.js     환경 변수 설정·기관 정보
  db/                    배포 후 자동 마이그레이션(migrate.js, migrations.generated.js)
  lib/                   D1 도우미, 세션, 비밀번호·(기존) PIN 해시, Web Crypto, 전화번호 정규화, 자동 이스케이프 템플릿, 라우터
  services/              신청·승인, 로그인 시도 제한, 비밀번호 재설정 코드, 게시판, 프로그램·회차, 관계망 자동 배정, 신청서·동의서 양식, Grow 신청, 출석, 감사기록
  como/                  꼬모 연동 어댑터 인터페이스, 전화번호 매핑
  routes/, views/        공개 · 참여자(/me) · 관리자(/admin) 영역
scripts/                 로컬 개발, 개발용 데이터, 관리자 생성, 원격 마이그레이션, 반응형 검수
test/                    자동 테스트
```

- 런타임 의존성은 없다(라우터·템플릿 자체 구현, Web Crypto 사용). 빌드 단계도 없다.
- 화면은 모두 서버(Functions)에서 렌더링한다. 클라이언트 JS는 비밀번호 보기/숨기기(`public/static/password.js`)뿐이며 없어도 동작한다.
- 신청·승인·게시판 데이터는 모두 D1(공유 DB)에 저장한다. 브라우저 저장소(localStorage 등)는 쓰지 않는다.
- D1은 대화형 트랜잭션이 없으므로 여러 쓰기는 `batch`(원자적)로, 정원 확인 신청은 단일 조건부 SQL로 처리한다.

## Cloudflare Pages 설정

저장소에 `wrangler.toml`을 두지 않는다. 바인딩·변수는 대시보드에서 설정한다
(Pages 프로젝트에 `wrangler.toml`이 있으면 그 파일이 우선해 대시보드 바인딩을 쓸 수 없다).

1. **D1 생성**: Workers & Pages → D1 → Create → 이름 `login-db`. 생성 후 database ID를 확인한다.
2. **스키마**: 따로 적용할 필요 없음. 배포된 앱이 첫 요청에서 `migrations/`를 자동 적용한다(아래 '배포 흐름').
3. **Pages 프로젝트 → Settings → Build**
   | 항목 | 값 |
   |---|---|
   | Framework preset | None |
   | Build command | (비움) |
   | Build output directory | `public` |
   | Root directory | (비움, 저장소 루트) |
   | Build variable | `SKIP_DEPENDENCY_INSTALL` = `1` (런타임 의존성이 없어 설치 불필요. 개발용 패키지 설치로 빌드가 느려지거나 실패하는 것을 막는다) |
4. **Settings → Bindings → Add → D1 database**: Variable name **`DB`**, 데이터베이스 `login-db`.
5. **Settings → Variables and Secrets** (Production)
   | 이름 | 종류 | 값 |
   |---|---|---|
   | `SESSION_SECRET` | Secret | 선택. 첫 관리자 지정(`/admin/setup`)에만 필요. 32자 이상 무작위 문자열 (예: `openssl rand -base64 48`) |
   | `CONSENT_JSON` | Text | 선택. 기본 동의문(`src/content/consent.js`) 대신 쓸 문안 JSON (`content/consent.example.json` 형식) |
   | `COMO_APPLY_URL` | Text | 선택. 기본 `https://cco-mho.pages.dev/` |
6. **재배포**(Deployments → Retry deployment). 바인딩·변수는 재배포 후 적용된다.
7. **관리자 계정**: 아래 '관리자 지정' 참고(사이트에서 처리, 콘솔 불필요)

### 참여 신청: 이름 · 휴대전화 번호 · 비밀번호

- 신청 화면 순서: 신청 시각(읽기 전용 안내 "신청 시각은 접수 완료 시 자동으로 기록됩니다.") → 이름 → 휴대전화 번호 → 비밀번호 → 비밀번호 확인 → 개인정보 수집·이용 동의 → 신청하기. 주소·우편번호·상세주소·생년월일과 카카오 주소 검색은 없앴다(기존 데이터는 지우지 않음).
- **최초 신청 시각**: 서버 입력 검증을 통과해 접수가 저장되는 그 SQL 문에서 D1 시각(`strftime('%Y-%m-%dT%H:%M:%fZ','now')`, 밀리초)으로 `registrations.registered_at`에 기록한다. 브라우저 시계나 요청 값은 쓰지 않으며, 이름 수정·로그인·새로고침·중복 제출로 바뀌지 않는다. 화면 표시는 한국시간 `YYYY-MM-DD HH:mm:ss`.
- **접수번호** = `registrations.id`. D1은 쓰기를 순서대로 처리하므로 접수번호 순서와 신청 시각 순서가 일치하고, 같은 초에 들어온 신청은 접수번호로 구분한다. 관리자 목록은 `registered_at, id` 오름차순과 접수순서(1, 2, 3…)를 보여 준다.
- **중복 방지**: `users.phone`·`registrations.user_id`가 UNIQUE라 같은 번호로 계정·접수가 두 번 생기지 않는다(동시 제출 포함). 전화번호는 하이픈·공백·+82를 정리한 숫자(`01012345678`)로 저장·비교한다.
- 신청 완료·내 신청정보·관리자 목록은 모두 **신청 시각 → 이름 → 전화번호 → 신청 상태** 순서. "신청 순서대로 검토하며 참여 확정은 담당자 확인 후 안내합니다." — 신청 순서로 자동 확정하지 않는다.

### 로그인: 휴대전화 번호 + 비밀번호

- 참여자는 `/login`에서 휴대전화 번호와 신청 때 정한 비밀번호로 로그인한다. 비밀번호 입력은 가려지고 보기/숨기기 버튼이 있다.
- 비밀번호: 8~64자, 영문+숫자, 휴대전화 번호 포함 불가. PBKDF2-SHA256(100,000회, Workers 상한) + 앱 비밀키(pepper)로 저장. 담당자도 볼 수 없다.
- 번호별 30분 내 5회 실패 시 잠금, IP별 1시간 내 30회 실패 시 차단. 실패 문구는 등록 여부와 무관하게 같다. 세션 쿠키는 HttpOnly·SameSite=Lax·(운영) Secure, 모든 POST에 CSRF 토큰 확인.
- **기존 PIN 계정 전환**: 비밀번호가 없는 계정은 비밀번호 칸에 기존 PIN 6자리를 넣어 로그인할 수 있고, 로그인 직후 `/account/password`에서 PIN을 다시 확인한 뒤 새 비밀번호를 정할 때까지 다른 화면이 막힌다. 새 비밀번호를 저장하면 `pin_hash`를 비워 PIN으로는 더 로그인할 수 없다. PIN·비밀번호 원문은 저장·표시하지 않는다.
- **비밀번호 분실**: 담당자(전체 관리자)가 본인 확인 후 신청자 상세(관리자는 `관리자` 메뉴)에서 **재설정 코드 발급** → 화면에 한 번 표시되는 8자리 코드(24시간, 1회용, 해시만 저장)를 전달 → 본인이 `/password/reset`에서 번호·코드·새 비밀번호 입력. 담당자는 비밀번호를 보거나 정하지 않는다. 코드 대입은 번호별·IP별로 잠근다.
- **전화번호 변경(본인)**: 승인 대기·승인 참여자 모두 `내 신청정보 → 전화번호 변경`에서 직접 바꾼다. 본인 계정만, **현재 비밀번호 재확인**, 형식 검사·하이픈/공백 정규화, 다른 계정 번호와 중복 차단. 계정 ID·비밀번호·승인 상태·게시글·신청기록(최초 신청 시각·접수번호)은 그대로이며 새 신청을 만들지 않는다. 바꾼 뒤에는 새 번호로만 로그인되고(이전 번호 불가) 다른 기기 로그인은 끊긴다. 변경 전·후 번호는 변경 기록(`audit_log`, `user.phone_change`)에 남는다. 담당자 승인은 필요 없다.
  - 문자 인증 기능은 없다(가짜 인증을 만들지 않았다). 새 번호 소유 확인이 필요하면 문자 인증 연동이 별도로 필요하다. 본인이 바꾼 번호는 '연락처 미확인'으로 돌아가며, 꼬모 매핑은 담당자가 연락처를 확인한 뒤에만 다시 한다.
  - 담당자도 신청자 상세에서 본인 확인 후 바꿀 수 있다(이때는 연락처 확인으로 기록).

### 이용 상태와 권한

| 상태 | 판정 | 이용 가능 |
|---|---|---|
| 비로그인 방문자 | — | 첫 화면(LOGIN : 人, 사업 소개, 네 영역 설명, 참여 대상·절차, 연락처), 참여 신청, 로그인, 신청서·동의서, 비밀번호 재설정 |
| 승인 대기 신청자 | 참여자, `is_selected=0` | 본인 신청정보(조회·전화번호 변경), 게시판(아래 권한) |
| 승인된 참여자 | 참여자, `is_selected=1`, `account_status='active'` | 프로그램 안내(상세 카드 포함), 나의 현황, 게시판, 내 신청정보(이름 수정) |
| 승인 해제 / 이용 중지 | `is_selected=0`(해제) / `account_status='suspended'` | 해제: 승인 대기와 같음 / 중지: 본인 신청정보만(게시판도 차단) |
| 관리자 | `staff` / `manager` | 관리 화면, 게시판 운영. 참여자 정원에 포함하지 않음 |

- 모든 화면·POST 요청·게시물 상세에서 서버가 로그인·역할·승인 상태를 다시 확인한다(`requireMember`, `requireSelected` 등). 사용자 정보는 요청마다 DB에서 읽으므로 승인 해제·이용 중지·로그아웃은 즉시 반영된다. 파일 다운로드 기능은 없다.
- **승인 최대 10명**: 담당자가 신청자를 확인하고 한 명씩 승인한다(자동 확정 없음). DB 트리거(`participants_cap_update`/`_insert`)가 승인된 이용 중 참여자가 10명을 넘는 변경을 거부하므로 동시에 승인해도 넘지 않는다. 이용 재개도 같은 제한을 받는다.

### 관리자 지정

1. Cloudflare Pages에 `SESSION_SECRET`(32자 이상)을 설정하고 재배포한다.
2. **첫 관리자**: `/admin/setup`을 열고(로그인 불필요) 1회용 설정 코드(해시만 `migrations/0009_setup_code.sql`에 있음, 원문은 개발 담당이 별도 전달) 또는 `SESSION_SECRET` 값, 이름, 휴대전화 번호, 새 비밀번호를 입력하면 전체 관리자 계정이 만들어진다. 이미 신청한 번호면 그 계정이 관리자가 되고 비밀번호가 새로 정해진다. 전체 관리자가 한 명이라도 있으면 이 화면은 닫힌다(404). IP별 1시간 10회 실패 시 잠금.
3. **다른 관리자**: 그 사람이 참여 신청을 한 뒤, 전체 관리자가 `신청자 → 상세 → 관리자 지정`에서 운영 담당/전체 관리자로 지정. `관리자` 메뉴에서 권한 변경·해제. 마지막 전체 관리자는 해제할 수 없다.

### 관리자 로그인: 아이디 + 비밀번호

- 관리자(운영 담당·전체 관리자)는 `/admin/login`에서 아이디·비밀번호로 로그인한다. 참여자는 `/login`(휴대전화 번호 + 비밀번호).
- 관리자로 지정된 뒤 처음 한 번은 번호·비밀번호(기존 PIN 계정은 PIN)로 로그인하고, `/admin/account`에서 관리자 아이디를 만들 때까지 다른 관리 화면은 열리지 않는다.
- 비밀번호: 8~64자, 영문+숫자, 아이디 포함 불가. PBKDF2-SHA256(100,000회) + 앱 비밀키(pepper)로 저장.
- 아이디별 30분 내 5회 실패 시 잠금, IP별 실패 제한은 참여자 로그인과 공유.
- 비밀번호를 잊으면 전체 관리자가 `관리자` 메뉴에서 **재설정 코드 발급** → 본인이 `/password/reset`에서 새 비밀번호. 본인 비밀번호는 `내 계정`에서 변경.

| 권한 | 할 수 있는 일 |
|---|---|
| 운영 담당(staff) | 프로그램·회차·출석, Grow 선정, 게시판 운영(공지 작성, 답변, 글 삭제), 관계망 자동 배정, 신청서·동의서 양식 등록 (참여자 전화번호는 가림) |
| 전체 관리자(manager) | 위 + 신청자 목록·승인·승인 해제·이용 중지, 전화번호 변경, 재설정 코드 발급, 연락처 확인, 꼬모 연동, 관리자 지정, 변경 기록 |

### 성장(Grow): 희망 신청 → 관리자 선정

- 참여자는 회차별로 `희망 신청`만 한다(선정 대기). 선정 대기 중에는 본인이 취소할 수 있다.
- 관리자는 `Grow 선정` 메뉴(또는 회차 화면)에서 선정·미선정·대기로 되돌리기를 한다. 정원은 선정 인원 기준이며 정원을 넘겨 선정할 수 없다.
- 선정된 신청만 참여자 일정(나의 현황)에 표시되고 출석을 기록할 수 있다.

### 게시판 (`/board`) — 로그인한 신청자(승인 대기 포함)와 담당자. 비로그인·이용 중지 계정은 차단

| 게시판 | 쓰기 | 수정·삭제 | 보기 |
|---|---|---|---|
| 공지사항 `/board/notice` | 담당자만 | 담당자 | 로그인한 신청자·담당자. 중요 공지는 맨 위 고정 |
| 자유게시판 `/board/free` | 신청자·담당자(글·댓글) | 본인 글·댓글, 담당자는 전체 삭제 | 로그인한 신청자·담당자 |
| 질문과 답변 `/board/qna` | 신청자·담당자(질문·답변) | 본인 질문·답변, 담당자는 전체 삭제 | 공개 범위 선택(기본 **담당자에게 비공개**): 비공개는 작성자·담당자만 보고 답변, 공개(**로그인 사용자에게 공개**)는 모두 보고 답변 |

- 담당자가 쓴 글·답변에는 '담당자'·'담당자 답변' 표시가 붙는다. 질문 목록에는 '담당자 답변 / 답변 n / 답변 대기'.
- 목록·글쓰기·상세·수정·삭제 확인·페이지 이동(15개)·검색. 비공개 질문은 목록·건수·검색·상세·답변 조회 SQL에서 걸러 다른 사용자에게 제목·내용·답변이 보이지 않는다(없는 글과 같이 404). 별도 JSON API는 없다.
- 게시판 첨부파일 기능은 없다(신청서·동의서 양식과 별개).
- 작성자 표시는 참여자 이름, 관리자는 '담당자'. 전화번호·신청 시각은 게시물 정보로 쓰지 않는다. 입력은 서버에서 길이·필수 검증, 출력은 자동 이스케이프.
- 기존 `notices`(공지) 데이터는 0011에서 공지사항 게시판으로 복사했고 원본 테이블은 남겨 두었다. `/notices`, `/admin/notices`는 게시판으로 이동한다.

`APP_ENV`를 지정하지 않으면 운영 모드다. `SESSION_SECRET` 없이도 모든 화면이 동작한다(첫 관리자 지정만 `SESSION_SECRET`이 필요). `DB` 바인딩이 없으면 모든 화면에 설정 오류 문구가 표시된다.

## 배포 흐름 (자동)

1. 변경은 브랜치 → PR로 올린다. GitHub Actions(`.github/workflows/ci.yml`)가 테스트(일반 + 로컬 D1)와 Functions 번들을 확인한다.
2. PR을 `main`에 머지하면 Cloudflare Pages Git 연동이 자동 배포한다.
3. 배포된 앱이 첫 요청에서 아직 적용되지 않은 D1 마이그레이션을 적용한다(`src/db/migrate.js`).
   - wrangler와 같은 `d1_migrations` 테이블을 쓰므로 CLI(`npm run db:migrate:remote`)와 섞어 써도 중복 적용되지 않는다.
   - 마이그레이션마다 기록과 함께 하나의 batch(트랜잭션)로 실행되고, 동시 요청이 있어도 한 번만 적용된다.
   - 실패하면 해당 마이그레이션 전체가 되돌려지고, 화면에 "데이터베이스 준비 중 오류"가 표시된다.
4. 마이그레이션을 추가할 때: `migrations/000N_설명.sql` 작성 → `npm run build:migrations` → 커밋.
   기존 버전 코드가 잠시 함께 돌 수 있으므로, 가능하면 컬럼 추가 위주로 작성하고 삭제는 다음 배포로 미룬다.

## 0011 마이그레이션과 복구

`migrations/0011_applications_boards.sql`은 컬럼·테이블·트리거·인덱스를 **추가**하고 프로그램 표기를 바꾼다. 기존 사용자·접수·동의·주소·생년월일·PIN·공지 데이터는 지우지 않는다.

- 추가: `users.account_status`, 승인 10명 트리거 2개, `registrations_order` 인덱스, `password_resets`, `posts`, `post_comments`(댓글·답변), `form_files`(양식 BLOB, 1.9MB 이하), `programs.archived_at`.
- 변경: 영역 재구성(L 정서 지원 ← 사례관리·전문 심리상담, O 관계망 형성 ← 요리교실·절기행사·나들이·김장나눔·자조모임), 최신(2차 수정본) 이름·일정·설명. 계획에서 빠진 `만남 및 교류활동`·`정서지원 키트`·`공예 체험`·`지역사회 인식개선 캠페인`은 `archived_at`으로 보관(삭제 아님, 관리자 프로그램 목록에만 '지난 계획(보관)'). 새 프로그램 3개(참여자 주도형 자조모임, 맞춤형 체험 활동, 평가회).
- DB의 영역 값은 내부 키 `L·O·G·IN` 그대로이며 화면에서만 `iN`으로 표시한다.
- **복구(되돌리기)**: 코드만 이전 버전으로 되돌려도 추가된 컬럼·테이블은 이전 코드에 영향이 없다. 스키마까지 되돌려야 하면 D1 콘솔에서 아래를 실행한다(게시판 글·재설정 코드는 사라지므로 먼저 내보내기).

```sql
DROP TRIGGER IF EXISTS participants_cap_update; DROP TRIGGER IF EXISTS participants_cap_insert;
DROP INDEX IF EXISTS registrations_order;
DROP TABLE IF EXISTS post_comments; DROP TABLE IF EXISTS posts; DROP TABLE IF EXISTS password_resets; DROP TABLE IF EXISTS form_files;
UPDATE programs SET archived_at = NULL, is_public = 1 WHERE code IN ('open-meetup', 'open-kit', 'grow-craft', 'in-campaign');
-- 영역·이름·일정 표기는 이전 값으로 되돌리려면 관리자 화면 또는 UPDATE로 고친다(D1 Time Travel 사용 권장).
DELETE FROM d1_migrations WHERE name = '0011_applications_boards.sql';
-- users.account_status, programs.archived_at 컬럼은 남겨도 이전 코드와 충돌하지 않는다.
```
- Cloudflare D1은 Time Travel(시점 복원, 무료 7일·유료 30일)을 지원하므로 배포 직전 시각으로 DB 전체를 되돌릴 수도 있다.

## 꼬모 연동 상태

- **확정·구현됨**: 상담 신청 경로(선정 확인 후 `COMO_APPLY_URL`로 이동, 전화번호 미전달), 전화번호 기준 매핑 정책과 충돌 처리.
- **미연결**: 상담 회차 자동 연동. 꼬모의 API·DB·관리자 권한이 제공되지 않아 실제 어댑터가 없다. 기본 상태(`COMO_ADAPTER=none`)에서 참여자 화면은 `연동 확인 필요`만 표시하고 회차 수치를 만들지 않는다.

연동 방식이 확인되면 `src/como/adapters.js`의 인터페이스(`findAccountsByPhone`, `getCounselingSummary`)를 구현한 어댑터를 추가하고 `config.js`의 `COMO_ADAPTER` 허용값에 등록한다. 필요한 반환값: 꼬모 계정 식별자, 완료 회차, 개인 총회차, (가능하면) 다음 상담 일정, 갱신 시각. 상담 내용·메모·진단은 받지 않는다.

매핑 규칙(`src/como/mapping.js`): 관리자가 확인한 번호만 사용 / 같은 번호에 꼬모 계정 여러 개, 이름 불일치, 이미 다른 사용자와 연결된 계정은 자동 연결하지 않고 관리자 확인 / 번호 변경 시 연결 해제·현황 삭제 후 재확인 / 연결 당시 번호와 현재 번호가 다르면 현황 미표시.

## 미확정 사항 (기관 확인 필요)

- **개인정보 보유·이용 기간과 파기 기준**: 동의문(`src/content/consent.js`, 버전 `2026-10-13`)의 보유 기간 문구("참여 종료·동의 철회 시 파기, 정산·감사 필요 정보는 사업 종료일(2027-12-13)로부터 5년")는 이전 문안을 그대로 두었다. 신청만 하고 승인되지 않은 사람의 정보, 게시판 글, 로그인 시도 기록의 보유 기간을 기관이 정해야 한다. 문안을 바꾸면 `version`도 바꾼다.
- **이전 방식으로 받은 주소·생년월일**: 기존 신청자 데이터에 남아 있다(신청자 상세의 '이전 등록 방식으로 받은 정보'에서만 보임). 보관 또는 파기 여부를 정하면 그에 맞게 처리한다(임의로 지우지 않았다).
- **신청서·동의서 양식**: 기관 승인 양식이 아직 없어 '양식 준비 중'으로 표시된다. 담당자가 `관리 → 신청서·동의서`에서 PDF(인쇄 화면 제공)·HWP·HWPX·DOCX 파일을 등록하면 바로 내려받기·인쇄가 열린다. 동의서 문구·보유기간은 기관 양식을 그대로 쓴다(임의 작성하지 않음).
- **참여 대상**: 중위소득 100% 이하 용인시에 거주 중인 북한이탈주민(첫 화면 표기). '우선순위' 기준 문구가 정해지면 반영한다.
- 전문 심리상담: 꼬모 상담 신청 연결을 그대로 두었다. '총 8회'는 사업 전체 운영 횟수이며 개인별 배정은 담당자가 관리한다(자동 예약 없음).
- 전화번호 변경 시 새 번호 문자 인증이 필요하면 별도 연동이 필요하다(현재는 현재 비밀번호 재확인).
- 꼬모 회차 연동이 실제로 연결되면 꼬모 측에 전화번호를 보내 조회하게 되므로, 별도의 제3자 제공 동의가 필요한지 확인한다.
- 꼬모 연동 인터페이스·통합 로그인 지원 여부.
- 프로그램별 실제 날짜·시간·장소·정원(관리자 화면에서 입력, 비어 있으면 '일정 미정').
- 기관 주소·전화(`src/site.js`, 시안 푸터 기준) 배포 전 재확인. 도메인(현재 `login-cpn.pages.dev`).
